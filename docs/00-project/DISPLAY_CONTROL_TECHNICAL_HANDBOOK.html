1. Executive summary

Display Control is a secure multi-customer digital-signage platform for Raspberry Pi screens. A central administration application lets authorized users manage customer organizations, users, screens, licences, media, playlists, groups, and schedules. Each Raspberry Pi independently connects to the central service, proves its identity with a client certificate, downloads only the content it is authorized to use, verifies every file, and displays it through a local Chromium kiosk.

The system is built around a fail-closed rule: if tenant identity, device identity, licence status, signed authorization, trusted time, media approval, or file integrity cannot be proven, the device must not display protected content. It shows Not licensed or another safe operational state instead.

The one-sentence architecture

The server decides and signs; the Pi agent verifies and enforces; the local React player only renders what the agent has authorized.

What is already implemented

  • Platform and tenant administration with invitation-only accounts and role-based access.
  • TOTP multifactor authentication, recovery codes, revocable server-side sessions, CSRF protection, and rate limiting.
  • Strict multi-tenant database isolation using application checks, Entity Framework filters, same-tenant foreign keys, and forced PostgreSQL Row-Level Security.
  • One-use Raspberry Pi enrollment, locally generated ECDSA keys, client certificates, mTLS authentication, certificate rotation, and revocation.
  • Device inventory and heartbeat reporting including serial, host, OS, software versions, disk, IP, and MAC information.
  • Per-device time-limited licences with renewal, suspension, revocation, transfer, and signed bounded offline leases.
  • Private content upload, file-signature inspection, SHA-256 hashing, ClamAV scanning, quarantine, approval, and immutable content versions.
  • Immutable playlists, device groups, direct/group assignments, priorities, and bounded scheduling.
  • Verified/resumable content downloads, local cache activation, and image/video/text playback.
  • Raspberry Pi systemd services, restricted service accounts, field-test packaging, and a virtual-device workflow.

What is not yet proven

  • Production infrastructure and operational readiness.
  • Physical Pi 4/5 playback, reboot, power-loss, clock, disk-pressure, and endurance evidence.
  • Real SMTP delivery and complete live-backend browser journeys.
  • Production monitoring, backup/restore, load testing, penetration testing, and signed agent updates.

2. Business problem and value

The platform solves a common remote-screen problem: an organization wants to control content shown on Raspberry Pi displays located on different networks without opening inbound access to those customer networks.

Business capabilities

  • Create isolated customer spaces.
  • Delegate access to customer administrators and content managers.
  • See which screens exist, where they are logically assigned, their network inventory, last contact, player health, and licence state.
  • Approve only safe content and publish stable playlists.
  • Target content to one device or a group, immediately or during a bounded time window.
  • Stop playback by suspending a device, tenant, licence, or certificate.
  • Allow limited offline playback without granting indefinite authorization.
  • Retain security/business audit evidence.

Design value

The architecture avoids LAN discovery and inbound router rules. Every Pi initiates outbound HTTPS to the public service. This is easier to deploy through NAT and usually safer than allowing the platform to reach into customer networks.

The system also separates content possession from content authorization. A file may remain cached on disk, but the player cannot access it after authorization is removed because the agent clears the local manifest and asset mapping.

4. System architecture

The selected architecture is a modular monolith. The backend runs as one ASP.NET Core application and one database, but responsibilities are separated into domain, application, infrastructure, HTTP, and background-worker components.

People Platform administrator ─┐ Tenant users ───────────┴── HTTPS, secure cookie, CSRF, MFA ──┐ ▼ React Admin SPA │ same origin ▼ Public server boundary ASP.NET Core Control Plane Reverse proxy / public TLS (production TBD) ───► ├─ Identity and tenancy ├─ Devices and certificates ├─ Licensing and signed leases ├─ Content and desired state ├─ Audit and notifications └─ Health and operations │ │ │ ▼ ▼ ▼ PostgreSQL Private ClamAV storage Raspberry Pi boundary C# Device Agent ── outbound HTTPS + client certificate ──────► API │ ├─ owner-only identity/state files ├─ verified media cache └─ loopback HTTP on 127.0.0.1:8787 │ ▼ React Player in Chromium kiosk

Why a modular monolith?

  • One backend is easier to deploy, debug, migrate, and explain than many services.
  • Transactions can atomically update business state and audit/notification intent.
  • The project still keeps explicit boundaries so a future split remains possible.
  • It fits the scope of an internship/project while preserving serious security controls.

Important architectural nuance

The intended layers exist, but the current Application project is relatively thin. It mainly contains interfaces, token/manifest codecs, file inspection, and storage/security contracts. A meaningful amount of use-case orchestration is currently implemented directly in API controllers and focused API services. This is acceptable for the current modular monolith but should be considered if business workflows become larger or need reuse outside HTTP.

Network model

  • Browsers communicate with the admin application and same-origin API.
  • Pis communicate outward to device API routes over HTTPS with a client certificate.
  • No public service connects inbound to a Pi.
  • The player server listens only on 127.0.0.1:8787.
  • Production documentation recommends separate admin and device hostnames so client-certificate handling does not complicate human traffic.

7. Data model

Most identifiers are application-generated UUIDs. Authorization timestamps are UTC. Licence and schedule windows use an inclusive start and exclusive end: [start, end). Tenant-owned rows contain a non-null tenant_id even when the tenant could be inferred through another row.

Identity and tenancy

  • Tenant: customer organization, slug, timezone, state, and concurrency token.
  • ApplicationUser: global ASP.NET Identity account with verified email and home-tenant locator.
  • TenantMembership: user-to-tenant role and lifecycle.
  • Invitation: target email, intended role, expiry, creator, and token digest.
  • UserSession: session digest, expiry, tenant binding, MFA state, revocation, and safe client fingerprints.
  • UserMfaSecret/UserRecoveryCode: protected TOTP secret and hashed one-use recovery codes.
  • IdentityNotification: protected invitation/reset payload and retry state.

Devices

  • Device: tenant-owned Pi, lifecycle, reported serial, host inventory, version, disk, last seen, and player state.
  • EnrollmentToken: short-lived, one-use capability with optional expected serial/device binding.
  • DeviceCertificate: certificate DER, fingerprints, public-key digest, validity, state, and rotation lineage. No private key is stored by the server.
  • DeviceHeartbeat: sequence, inventory snapshot, applied desired state, player/disk state, public source address, and correlation ID.
  • DeviceNetworkInterface: latest interface, normalized MAC, local addresses, and observation time.

Licensing

  • DeviceLicense: device, validity window, control state, latest issued lease boundary, transfer destination, and concurrency token.
  • LicenseEvent: append-oriented lifecycle event with actor, reason, before/after snapshots, and device lineage.

Content and scheduling

  • ContentAsset: logical title/media kind and lifecycle.
  • ContentVersion: immutable storage reference, byte length, SHA-256, MIME, metadata, scan result, and approval.
  • Playlist/PlaylistVersion/PlaylistItem: logical playlist plus immutable ordered published version.
  • DeviceGroup/DeviceGroupMember: tenant group membership.
  • DeviceAssignment/GroupAssignment: target, playlist version, priority, UTC window, and presentation timezone.
  • DesiredState/DesiredStateAsset: immutable, device-specific compiled manifest with monotonic version and manifest digest.

Operational records

  • TenantAuditEvent: actor, action, target, outcome, reason, correlation ID, and bounded JSON details.
  • OutboxMessage: generic transactional-outbox shape.
  • SystemKeyMetadata: public key metadata and activation/retirement dates.

8. Human identity workflows

8.1 First platform administrator

  1. Deployment generates a high-entropy bootstrap token and stores only its SHA-256 digest in API configuration.
  2. An operator calls the platform-bootstrap endpoint with email, display name, password, and token.
  3. The endpoint is rate-limited to three attempts per hour per source address.
  4. If a platform administrator already exists, bootstrap becomes logically unavailable.
  5. The created account must enroll TOTP at first sign-in.

8.2 Session bootstrap and CSRF

  1. The browser loads the administration SPA and calls GET /api/v1/session.
  2. The API returns anonymous/authenticated session state and issues a protected CSRF cookie/token pair.
  3. The React app keeps the returned CSRF token in memory and sends it in X-CSRF-TOKEN for unsafe requests.
  4. The global antiforgery filter rejects unsafe cookie-based requests without a valid token before business work occurs.

8.3 Sign-in and MFA

  1. Email/password are processed through ASP.NET Core Identity with neutral failure behavior and rate limiting.
  2. A server-side UserSession is created; the browser receives an opaque secure cookie.
  3. If an administrator has no confirmed MFA secret, the session enters mfa_enrollment.
  4. The user registers a generated TOTP secret in an authenticator and confirms a six-digit code.
  5. Ten one-use recovery codes are displayed once. Only digests are stored.
  6. Future sign-ins enter mfa_pending until TOTP succeeds.
  7. Each accepted TOTP time step is persisted so the same code window cannot be replayed.

8.4 Session validation

Authentication is not trusted only because a cookie exists. On each request, middleware verifies the session digest, user, security stamp, expiry, revocation state, home tenant, tenant state, membership state, and current role. A changed role or suspended membership is therefore enforced without waiting for the eight-hour cookie expiry.

8.5 Recent MFA

Sensitive actions require an MFA proof no older than ten minutes. The user can enter a current code through the step-up endpoint. Examples include role changes, certificate revocation, licence transfer, recovery-code regeneration, global sign-out, and sensitive platform tenant actions.

8.6 Password recovery

  1. The forgot-password response is identical whether or not an account exists.
  2. For an eligible account, a short-lived reset token is wrapped in a protected notification payload and queued.
  3. The notification worker builds an encoded public HTTPS reset link and delivers it via TLS-enabled SMTP.
  4. Successful password reset updates the security stamp and revokes prior sessions.

9. Tenant administration workflows

9.1 Creating a customer

  1. A platform administrator with recent MFA submits tenant name, slug, timezone, first-admin email, and first-admin role.
  2. The API creates the tenant and a tenant-bound one-use invitation.
  3. The raw invitation token is displayed or sent only once; the database stores a digest.
  4. The invited administrator accepts the link, chooses a display name/password, then enrolls MFA.

9.2 Tenant lifecycle

  • Active: normal user and device operation.
  • Suspended: human sessions are revoked and subsequent device authentication/heartbeats are rejected.
  • Archived: terminal state; the tenant cannot be modified or reactivated.

9.3 Member lifecycle

A tenant administrator can invite members, list them, change roles, suspend/reactivate/remove access, and see MFA state. Role changes and membership restrictions revoke affected sessions. Domain rules preserve lifecycle consistency and project requirements include protecting the last-administrator invariant.

10. Raspberry Pi identity and heartbeat workflows

10.1 Enrollment code creation

A tenant administrator creates a pending device and a high-entropy, one-use enrollment code. The code can be bound to an expected serial number and normally expires after 15 minutes. Only its HMAC-SHA256 digest is persisted.

10.2 Device enrollment

  1. The Pi reads its serial from /proc/cpuinfo, gathers host/network/disk inventory, and generates an ECDSA P-256 private key locally.
  2. The private key is written to an owner-only file. The Pi sends only a certificate-signing request, enrollment code, and inventory.
  3. The API rate-limits the request, identifies the tenant from the capability token, checks expiry/use/attempt count/expected serial, and atomically consumes it.
  4. The certificate authority issues a client certificate containing tenant and device identity extensions.
  5. The response includes the public CA, certificate, server UTC, and pinned licence-verification public key.
  6. The Pi verifies the certificate matches its private key, validates the chain against the returned CA, validates the signing public key, and persists state atomically.
  7. Only after successful persistence does it delete the temporary enrollment-code file.

10.3 Device authentication

Device API routes require a presented client certificate. Custom middleware rebuilds the chain against the configured device CA, reads the identity extensions, verifies certificate time and cryptographic properties, then verifies the certificate record, device state, and tenant state in PostgreSQL. It creates a device-only principal containing tenant, device, certificate, and mTLS claims.

10.4 Certificate rotation

When the current certificate has 30 days or less remaining, the agent creates a separate next private key and CSR. The API issues a replacement certificate and limits overlap of the old certificate. The agent verifies that the CA has not changed and that the certificate matches the pending key. State is written before the key is promoted, and recovery logic handles interruption between those operations.

10.5 Heartbeats

  1. Every configured interval (normally 30 seconds plus 0–2 seconds jitter), the agent collects fresh inventory.
  2. It sends an increasing sequence number, player state, applied desired-state version, disk information, and interface snapshot.
  3. The server rejects repeated/out-of-order sequence numbers.
  4. The current device row is updated and a heartbeat history row is appended.
  5. Network-interface rows are replaced with the current normalized snapshot.
  6. The server evaluates licence and desired state, then returns either denial or a signed lease.

11. Licensing and offline authorization

11.1 Licence states

11.2 Signed offline lease

The server signs leases with ECDSA P-256 using ES256. A lease binds at least:

  • tenant, device, certificate, and licence identifiers;
  • issue, not-before, and not-after timestamps;
  • desired-state identifier/version and manifest SHA-256, when content exists;
  • a signing-key identifier, algorithm, schema version, and unique token identifier.

The expiry is the earliest applicable boundary:

lease expiry = minimum of: authenticated server time + configured offline allowance (maximum 24 hours) actual licence expiry device certificate expiry assignment/schedule end, when one exists

11.3 Trusted time

The agent anchors time to the most recent authenticated server UTC plus monotonic elapsed time during the process lifetime. It rejects an authenticated server time that rolls back beyond tolerance. If the network fails during the same boot, a valid cached lease can continue to authorize already-active content until expiry.

Deliberate availability trade-off: after an agent restart with no authenticated server contact, the in-memory monotonic anchor is unavailable. The agent fails closed rather than trusting the Pi wall clock. Cached files may exist, but playback is not authorized until server time is re-established.

11.4 Licence transfer

A transfer cannot instantly authorize both source and destination. The destination licence begins no earlier than the latest issued source lease expiry. This prevents a normal transfer operation from creating overlapping authorized playback.

12. Content, playlists, and scheduling

12.1 Upload and inspection

  1. The content manager selects title, declared media kind, and file.
  2. The API enforces configured request/object size limits. The current default object ceiling is 256 MiB.
  3. The file inspector streams the bytes, calculates SHA-256, and validates actual signature against the declared kind.
  4. PNG/JPEG dimensions are bounded; text must be valid UTF-8 without unsafe control characters; WebP and MP4 signatures are recognized.
  5. The private object store writes to a temporary file and atomically publishes it without overwrite.
  6. ClamAV scans the stored bytes through a bounded streaming protocol.
  7. Clean content becomes a draft; infected content is rejected; scanner failure keeps it quarantined.
  8. A content manager must explicitly approve a clean draft before playlist use.

12.2 Private storage

Media bytes are not stored in PostgreSQL and are not placed in a public web root. Code addresses objects using a key made only from normalized tenant and object UUIDs. Browser filenames and device inputs cannot become filesystem paths. The local adapter rejects links/reparse points, length mismatches, oversize streams, and overwrites.

12.3 Playlists

A logical playlist is created with ordered items that refer to approved content versions. Publication freezes a playlist version. The immutable snapshot records content identifiers, order, image/text durations, video looping, and presentation data.

12.4 Assignments and schedule resolution

  • A playlist version can be assigned directly to a device or to a device group.
  • Bounds are optional UTC instants using [start, end).
  • Priority is between -1000 and 1000.
  • Direct-device assignment always outranks group assignment.
  • Within the same class, highest numeric priority wins.
  • If the two leading active candidates have equal priority, the resolver throws an ambiguity error rather than choosing arbitrarily.
  • Recurring schedules are intentionally outside v1.

12.5 Desired-state compilation

Publishing an assignment verifies that its playlist is immutable/published and that every referenced content version is still clean and approved. The server flattens it into a device-specific desired state with a monotonic version and canonical manifest SHA-256. That digest is later included in the signed lease.

13. Synchronization, cache, and playback

13.1 Authorization response

A licensed heartbeat returns server time, retry advice, a signed lease, the licence expiry, and either licensedNoContent or an available desired-state identifier/version. An unlicensed heartbeat returns no lease and a not-licensed desired-state summary.

13.2 Agent validation

  1. Verify authenticated server time does not move backward unexpectedly.
  2. Verify lease key identifier, algorithm, and public key match the pinned verification key.
  3. Verify the ES256 signature and tenant/device/certificate/time bindings.
  4. Verify the desired-state response matches the lease payload.
  5. Persist authorization state atomically before synchronization.

13.3 Manifest and asset synchronization

  1. The player enters Synchronizing and its previous manifest is removed from the browser-facing state.
  2. The agent requests the authorized manifest through the device API.
  3. Manifest size, ID, version, time bounds, asset count/order, unique IDs, media kinds, durations, lengths, and SHA-256 fields are validated.
  4. The canonical manifest SHA-256 must match the value signed into the lease.
  5. Existing cached objects are rehashed before reuse.
  6. Missing assets download into a private staging directory.
  7. Interrupted downloads resume using HTTP Range. Content-Range and response length are verified.
  8. The agent hashes the entire final object and rejects length/digest mismatch.
  9. Verified objects and manifest are atomically promoted; stale inactive manifests are removed.
  10. The agent exposes a sanitized in-memory manifest to the local player and records the applied version.

13.4 Cache pressure

The default cache ceiling is 4 GiB with a 256 MiB free-disk reserve. Before download, the agent calculates required object and filesystem space. It removes least-recently-written inactive objects while protecting active hashes. If the replacement cannot fit safely, synchronization fails without partially authorizing it.

13.5 Local player

The agent hosts static player files and four loopback endpoints: health, player state, manifest, and authorized asset bytes. Assets are served only when present in the active in-memory mapping; physical paths are never returned to React.

Player stateMeaningUI
notLicensedNo valid authorization or an error makes authorization uncertain.Exact message “Not licensed”.
noContentLicence is valid but no assignment resolves.“No content assigned”.
synchronizingAuthorization exists but active content is not ready.Synchronization indicator.
readyManifest and assets are verified and active.Ordered image, video, or text playback.

The React player polls local state every five seconds. Images/text advance by configured duration. Non-looping video advances on its ended event; looping video remains on the same item. If agent state or manifest loading fails, React returns to the safe default.

14. Email notification workflow

Notification delivery is optional and starts only when enabled by configuration. Invitation and password-reset payloads are protected using an independent ASP.NET Core Data Protection purpose before database insertion.

  1. The web transaction enqueues a protected notification but its restricted runtime role cannot read notification payloads back.
  2. A separate worker connection uses a separately restricted PostgreSQL role.
  3. The worker sets an explicit notification-delivery context and claims one due row using FOR UPDATE SKIP LOCKED.
  4. It verifies the protection scheme and unprotects only the selected payload.
  5. It creates the appropriate invitation/reset message and sends it through TLS-enabled SMTP.
  6. Success marks the row processed. Failure stores only a safe error code and schedules progressive retry.
Status: the worker and security behavior exist and are tested at code level, but real delivery through a staging SMTP provider is still an open acceptance item.

15. Security model and controls

15.1 Defense in depth for tenant isolation

  1. The browser does not choose an authoritative tenant; the authenticated session does.
  2. Authorization compares a tenant route to current membership.
  3. Middleware creates a scoped trusted tenant context.
  4. Tenant-owned database work runs inside a transaction that uses PostgreSQL set_config('app.tenant_id', ..., true).
  5. The final true makes context transaction-local so pooled connections do not leak tenant state.
  6. EF query filters default-deny when context is missing.
  7. Forced PostgreSQL RLS policies enforce the same boundary in the database.
  8. Composite foreign keys prevent cross-tenant relationships.
  9. The runtime database role is neither owner, superuser, nor BYPASSRLS.

15.2 Human security controls

  • Invitation-only onboarding; one-use expiring tokens stored as digests.
  • Unique verified email, password hashing configured to 210,000 iterations, and account lockout.
  • TOTP MFA, time-step replay guard, one-use recovery codes, and recent-MFA step-up.
  • Opaque server-side sessions with security-stamp validation, idle/absolute expiry, and revocation.
  • Secure __Host- cookies: HTTPS-only, HttpOnly, SameSite Strict, root path.
  • CSRF protection on unsafe cookie-based routes.
  • Neutral authentication/recovery errors and endpoint-specific rate limits.

15.3 Device security controls

  • Human and device identity systems are separate.
  • Enrollment token is only a bootstrap capability, not a long-term credential.
  • Device private key originates and stays on the Pi.
  • Only ECDSA P-256 CSRs/certificates are accepted.
  • mTLS identity is bound to tenant, device, certificate record, device state, and tenant state.
  • Certificate rotation uses proof of possession and bounded overlap.
  • Heartbeat sequence prevents basic replay/out-of-order processing.
  • Signed leases bind authorization to certificate and manifest.

15.4 Content security controls

  • Private storage with opaque UUID-derived keys and no public directory.
  • Bounded streaming rather than trusting complete in-memory uploads.
  • Declared type must match magic bytes; invalid UTF-8/control text is rejected.
  • Malware scan is fail-closed; approval is a separate explicit action.
  • Published content/playlist/manifests are immutable.
  • Every downloaded object and manifest is checked with SHA-256.
  • HTML, JavaScript, executable uploads, and scriptable SVG are not supported.

15.5 Web and service hardening

  • Security headers: no server banner, HSTS outside development/testing, CSP, nosniff, no-referrer, and restrictive permissions policy.
  • No explicit permissive CORS configuration; the admin design is same-origin.
  • OpenAPI is exposed only in development.
  • API errors use bounded Problem Details rather than raw exception content.
  • Pi services run under restricted accounts with systemd hardening and no extra capabilities.
  • Chromium keeps its sandbox; the launcher does not use --no-sandbox or a remote-debugging port.
  • State/cache code rejects symbolic links and Windows reparse points.

18. Development and deployment

18.1 Developer prerequisites

  • .NET SDK 10.0.203 exactly.
  • Node.js 24 or 25 and npm 11.
  • Docker Desktop/Engine with Compose v2.
  • Git and PowerShell 5.1+ locally.

18.2 Local services and secrets

Docker Compose exposes PostgreSQL and ClamAV only on loopback. The API refuses to start outside testing when essential configuration is missing or unsafe. Required production-style inputs include:

  • restricted PostgreSQL connection string;
  • absolute Data Protection key directory;
  • at least 32 random bytes of token-digest pepper;
  • device CA PFX and password;
  • encrypted ECDSA licence-signing key and password;
  • absolute private content root;
  • ClamAV endpoint and offline-allowance setting.

The development helper creates local-only security material beneath ignored .data. It is not a production key-management solution.

18.3 Database identities

  • Migration owner: owns schema and applies reviewed migrations; unavailable to the web process.
  • Web runtime: no superuser/owner/BYPASSRLS; narrow table operations; can insert but not read notification payloads.
  • Notification worker: separate connection/role; only select/update notification rows under a special RLS context.
  • Production backup and monitoring identities must also be separate.

18.4 Pi release and installation

  1. Build the React player.
  2. Publish the .NET agent self-contained for linux-arm64, embedding player assets.
  3. Create a versioned tar.gz and SHA-256 file.
  4. On aarch64 Raspberry Pi OS, run the root installer with server URL, trusted digest, version, enrollment-code file, optional field CA, and graphical kiosk user.
  5. The installer verifies architecture and artifact SHA-256, creates service identities/directories, installs a root-owned immutable release, and atomically updates /opt/display-control/current.
  6. It configures agent state/cache limits and enables agent/kiosk services.
  7. The enrollment file is removed after successful enrollment.

18.5 systemd hardening

The agent and kiosk run under different users. Units remove capabilities, enable NoNewPrivileges, restrict writable paths and address families, protect system/home/kernel/control groups, use private temporary directories, apply owner-only umask, and restart failed services. Chromium keeps its normal sandbox.

18.6 CI pipeline

The GitHub workflow checks out without persistent credentials, installs pinned SDKs, restores locked dependencies, builds/tests .NET, installs npm dependencies with npm ci --ignore-scripts, runs production dependency audit, lint, type checking, React tests/builds, installs Chromium, runs Playwright, validates documentation traceability, validates Compose configuration, and uploads test/failure artifacts.

21. Manager talking points and questions

60-second presentation

Display Control is a secure multi-tenant digital-signage platform. Administrators manage customers, users, Raspberry Pi screens, licences, media, playlists, and schedules in a React web application. Each Pi makes an outbound connection to an ASP.NET Core API, authenticates with its own certificate, verifies a signed time-limited licence decision, downloads only approved content, checks every file, and plays it locally through Chromium. The main secure workflow works locally; the remaining work is physical hardware validation and production operations/security evidence.

Five points to emphasize

  1. It is more than a media player: it manages authorization, identity, tenant isolation, content safety, synchronization, and operational state.
  2. The Pi is outbound-only: customer routers do not need inbound access.
  3. Offline is bounded: cached content cannot be authorized indefinitely; the lease is capped at 24 hours and other earlier boundaries.
  4. Security is layered: roles, MFA, sessions, CSRF, mTLS, RLS, private storage, malware scanning, signatures, hashes, and restricted services work together.
  5. Status is honest: the vertical slice is implemented and locally tested, but physical and production evidence remain required.

Likely questions and suggested answers

QuestionSuggested answer
Why not microservices?A modular monolith reduces deployment and transactional complexity while preserving clear internal boundaries. It is appropriate for the current scope and team size.
How are customers isolated?The session establishes tenant context; authorization checks it; EF filters it; PostgreSQL forced RLS enforces it; same-tenant foreign keys prevent cross-tenant relationships.
What happens when Internet fails?Already-ready cached playback can continue only while a signed lease remains valid during the same boot. When authorization cannot be proven, the device shows Not licensed.
Can a user copy content URLs?Media is private and not in the public web root. The Pi receives only device-scoped resources, and the browser sees only loopback URLs currently authorized by the agent.
What if a Pi is stolen?Certificates/devices can be revoked, but a determined person with root/physical access may extract software-held credentials/cache. Hardware-backed security is outside the current baseline.
Is it production-ready?No. The architecture and core workflow are strong, but production infrastructure, physical Pi acceptance, operational controls, load/security testing, and final evidence remain.
What is the biggest technical strength?The authorization chain: isolated tenant data leads to a signed device/certificate/manifest-bound lease that the Pi independently verifies before exposing local content.
What is the biggest project risk?Moving from locally verified software to a production-operated system: real hardware, public TLS/edge, secrets, storage, monitoring, backup/restore, capacity, and independent security evidence.

Things not to claim yet

  • “Production-ready,” “penetration-tested,” or “fully secure.”
  • Validated Pi 4/5 GPU/video performance.
  • Validated real-email delivery.
  • Proven production-scale fleet capacity.
  • Proven disaster recovery or zero data loss.
  • Complete WCAG conformance based only on automated axe checks.
